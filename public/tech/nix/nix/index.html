Nixのことがよくわからないあなたと私がふわっと理解するための入門記事

April 29, 2026

はじめに#

ながすなりです。

Nixというものをどこかで見かけました。よくわからなかったので、調べてみようと思いました。こんな小学生みたいな動機で書き始めていますので、もちろん間違いも勘違いもたくさんあると思いますが、この記事を読み終わった後にふわっとNixのことがわかっているくらいを目標にしているため悪しからず。

まずNixってナンジャラホイ#

まず公式のgithub1から説明をいただきましょう。

Nix is a powerful package manager for Linux and other Unix systems that makes package management reliable and reproducible.

僭越ながら簡単に日本語訳させていただくと、“NixはLinuxや他のUnixのための強力なパッケージマネージャで再現可能で信頼できるパッケージ管理を提供します"的なことが言われています。

私の理解の方法にお付き合いいただきたいのですが、こう言った物事を定義する文言にぶつかったときにはちょっとでも曖昧な言葉を完全に理解していくのが私の好みです。まず一つ目パッケージマネージャってなんなのでしょう？いやもちろんふわっとはわかってるつもりです。JSならnpm, Pythonならpipといわゆるパッケージマネージャについてはなんとなくわかっていますし、依存関係を管理するシステムだということも理解しています。ただその動作原理はよくわかっていません。加えて、JSのためのパッケージマネージャはnpmだと思いますが、Linuxのためのパッケージマネージャとはどういうことでしょうか？理解に近そうなのは、HomeBrewとかaptですが…本当にそれが一致しているのかがよくわかりません。これを一つ目の曖昧さとします。

二つ目は再現可能で信頼できるとわざわざいうのはなぜでしょうか？npmもuvもpackage.jsonに類するものがあれば、再現可能で信頼できるような気がします。他のパッケージマネージャも持っている特徴をわざわざ論うことはないでしょうから、Nix特有の何かがきっとあるのでしょう。この辺も明確にしたいものです。

ですが現時点でとりあえずNix = パッケージマネージャということは理解できました。ここから少しずつその特徴に迫っていきましょう。

パッケージマネージャってなんだ？#

素晴らしいまとめ記事2がありましたので、引用させていただきます。この記事ではパッケージマネージャを以下のように定義しています。

  1. パッケージリポジトリからパッケージをダウンロードする
  2. パッケージの依存関係を自動的に解決する
  3. ビルドシステムを持つ
  4. パッケージのインストールを自動的に行う

まあ正直何が何やらという気がするので、実際に具体例を用いて考えてみましょう。

パッケージリポジトリからパッケージをダウンロードする#

いわゆるinstallコマンドでしょう。npm install <package>を叩くと、パッケージのリポジトリにアクセスして該当パッケージをローカル環境に持ってくるというのがこのコマンドですね。

パッケージの依存関係を自動的に解決する#

これはpackage.jsonとpackage-lock.jsonの参照に対応するでしょう。例えばパッケージAにはパッケージBのバージョン2.0以上が必要という条件があった場合、npmがそれをよしなに管理してくれます。またパッケージCが同様にパッケージBのバージョン3.0以上が必要だった場合のバージョンの競合などの解決も担っています。

ビルドシステムを持つ#

これはnpm run buildが対応すると思います…が個人的には私はこれをパッケージマネージャの特徴とするのはいささかの疑問があります。大体npm run buildは以下のように他のツール呼び出すための、トリガーというかエイリアスのようなイメージです。もちろんRustのCargoのように強力なビルドシステムを持つパッケージマネージャもありますが、パッケージマネージャ全体の特徴にしておいていいかは、諸説ありかなぁと思います。ただモダンなパッケージマネージャはビルドシステムを持ちがちくらいに本記事では留めておきましょう。Goとかも持ってるはずですし。

{
  "scripts": {
    "build": "vite build"  // または "tsc", "webpack", "next build" など
  }
}

パッケージのインストールを自動的に行う#

これはnode_modulesへの配置とそこにパスを通すことまでを指すと思います。ダウンロードしてきたファイルを解凍して、パスを通して即座に使える状態までにすることまでを指すかなと。

なんとなくパッケージマネージャの全体像が見えてきました。おそらく狭義のよりピュアなパッケージマネージャの定義は1,2,4だと思います。リポジトリからパッケージをダウンロードしてきて、適切な場所に配置し、適切なパスを追加する。そしてそのバージョンや依存関係の管理をするためのソフトウェアという理解できっとほとんど外さないでしょう。

再現可能で信頼できるってどういうこと？#

この記事に完璧に書いてありました3。正直私の書いていることは大体この方の記事をさらに噛み砕いていることになりかけているので、存在意義があるのか怪しくなっています。

再現可能#

“Nix builds packages in isolation from each other. This ensures that they are reproducible and don’t have undeclared dependencies, so if a package works on one machine, it will also work on another.”

「Nixはパッケージを互いに隔離してビルドします。これにより、パッケージが再現可能であり、未宣言の依存関係を持たないことが保証されます。もしパッケージが1つのマシンで動作するなら、別のマシンでも動作するでしょう。」

…他のパッケージマネージャも再現可能では？と私なんかは思ってしまうのですがどうなんでしょうか？調べてもよくわからなかったので、Geminiちゃんに聞きました。彼女曰く、その肝は依存関係の底がどこにあるかということにあるらしいです。npmやcargoはコンパイラやOSのシステムライブラリまでは管理しませんが、Nixはコンパイラから何から何までを/nix/storeで管理するようなのです。他のパッケージマネージャがホストOSなどを参照してしまうのに対し、Nixは純粋に/nix/storeの中の依存関係だけを参照してビルド・実行するため、どんなPCや環境でも再現可能であり、強力な再現可能性が担保されるというわけらしいです。

信頼性#

“Nix ensures that installing or upgrading one package cannot break other packages. It allows you to roll back to previous versions, and ensures that no package is in an inconsistent state during an upgrade.”

「Nixは、1つのパッケージをインストールまたはアップグレードすることが他のパッケージを壊すことができないようにします。また、以前のバージョンにロールバックすることができ、アップグレード中にパッケージが不整合な状態になることがないようにします。」

これは割とそのままで理解できますね。ので特に解説なしで。

またこのあたりのことを調べていると純粋関数的であるというような表現が出てきます。これもきちんと整理しておきましょう。純粋関数にはルールが二つあって、一つ目は同じ入力に対して同じ出力を返すことで、二つ目は外部の状態に影響を与えない、つまり副作用がないということです。 おそらくこの表現が言いたいこととしては、再現可能の部分と同じようなことで、他のパッケージマネージャがホストOSなどの状態によって結果が変わってしまうのに対し、Nixは常に結果が不変であるということを指したいのではないかと思います。

使ってみる#

お待たせしました。それでは使ってみましょう。これまでの章で、とりあえずめちゃくちゃ厳密なパッケージマネージャという印象を受けましたが、その実力はどうなんでしょうか？使ってみましょう。

まずインストール4です。コマンド一つなので楽ですね。

curl -L https://nixos.org/nix/install | sh

これだけで簡単に入るのは嬉しいですね。
